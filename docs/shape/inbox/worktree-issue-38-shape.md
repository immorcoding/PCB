## Proposed（清 inbox 时交给用户过一遍；用户已在票上同意内容，级别按 exploring）

对 **PROC-15** 的补充，或拆成新的规则，由清 inbox 的会话定编号：

1. **基准夹具跟着工具、按情况不按板。** 工具的基准夹具（`tests/<工具>/fixture/`）按它代表的情况命名和增加（间距、层数、拓扑），不带板名；新板只在带来现有夹具没覆盖的情况时才加一个。板子自己的规则基准板（`rules_cases.py`）仍是每块板一份。 _Why:_ 现有夹具是从 H743 冻结出来的，带着它的规则区名和网络类；每块板一套会让基准随板子数量增长，改工具时不知道哪套算数。
2. **做完的板定在一个工具标签上，不当回归基准。** 板子交付后在 main 上打标签并写进它的 SPEC（用这个提交的工具可逐字节重建）；之后工具改动不要求它还能重建。改工具的把关靠 `regress`：每次改跑该工具自己的基准，PR 合并前跑整套；预期数字因通用化而变时更新并写明原因。 _Why:_ 板子的走线文件直接调用工具接口，工具面向通用修改后必然漂移；全量重建约 27 分钟，绑在每次修改上反馈回路太慢（PROC-6）。
3. **现有工具的修改走独立的执行 issue，每张一个分支、一个 PR 进 main；原型留在分支。** 通用化和修缺陷的修改和建板的 issue 分开，排在用到它的那个阶段之前合进 main；原型、验证板、新工具的原型留在各自的分支，达标后按本条重写转正。在板上发现已合并的修改不对，再开执行 issue 改，不在板子的分支上就地修工具。 _Why:_ 修改攒在板子的分支上会和板子数据混成一个大合并，也绕开了基准。
4. **现有工具在新板型上先清查、再分类、再验。** 新板型开工前清查工具里写死的板型假定，把工具分成：原样验、小改后验、通用化后验、不验（冻结或被接替）。通过 = 只写数据文件就能跑完、输出至少 3 处和独立来源对上、指标表能进 `compare_runs`；结果记在板目录的 `TOOLS.md`，交付时并进审查清单。不通过时：挡住阶段的修工具并加复现的夹具；写死的值挪到数据文件；用不到的记“不适用”；不挡阶段的记待办。 _Why:_ 首次摸底只跑了三个工具就有两个给不出结论；没有口径时“能跑”会被当成“通过”。
